# Diabetes Model Demo Artifacts

These files are generated by:

```bash
.venv/bin/python -m services.diabetes_model.generate_demo_artifacts
```

The generator uses a deterministic balanced selection of 20 training patients,
then the standard 10-patient validation and 10-patient test split. The outputs
demonstrate the complete ML flow for the proposal and backend handoff:

- `diabetes_random_forest.joblib`: fitted Random Forest for trusted local use
- `diabetes_random_forest.metadata.json`: inspectable model/API contract
- `training_accuracy_curve.png` and `training_summary.json`: model selection
- `test_evaluation.json`: one-time held-out evaluation
- `feature_importance.png` and `feature_importance.json`: global split importance
- `backend_prediction_example.json`: example JSON request and response
- `training_session_response.json`: full response for one 20-patient selection
- `selection_robustness.json` and `.png`: variability across 30 valid selections
- `model_benchmark.json` and `.png`: Random Forest versus two reference models
- `selection_assessment_examples.json`: ready, warning, and error examples
- `artifact_manifest.json`: file sizes, SHA-256 checksums, and runtime versions
- `patient_split.json`: exact patient IDs used in the demo split

Only load the `.joblib` file when it comes from this trusted repository. The
feature importance is a model splitting statistic, not causal evidence or
clinical importance.

They are not clinical results and are not representative of real diabetes
prevalence or diagnostic performance. A student's different training selection
will produce different model scores and metrics.

Verify the generated delivery files from the repository root:

```bash
.venv/bin/python -m services.diabetes_model.artifact_manifest \
  artifacts/diabetes_demo/artifact_manifest.json
```

The checksum manifest detects file changes but is not a digital signature.
